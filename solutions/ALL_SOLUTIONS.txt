==== LAB: c01-bare-ip-404 ====

C01 - BARE-IP 404 FINGERPRINT
=====================================
Lab      : c01-bare-ip-404
Case     : C1 (writeup para 11-14)
Ports    : HTTP 18080, HTTPS 18443
Start    : make up LAB=c01-bare-ip-404
Verify   : make verify LAB=c01-bare-ip-404      (13 assertions)

OBJECTIVE
  One IP answers on 443 with nothing useful. Establish that a virtual-host router
  is in front and your request has no hostname it recognises, then prove the
  contrast with a hostname it does know.

STEP 1 - the wall
  curl -skD - -o /dev/null https://127.0.0.1:18443/ | tr -d '\r'

  expected (h2 by default; HEAD omits content-length, a GET does not):
    HTTP/2 404
    content-type: text/html
    server: Microsoft-HTTPAPI/2.0
    content-length: 0

  add --http1.1 to see the classic line: HTTP/1.1 404 Not Found

  Microsoft-HTTPAPI/2.0 is http.sys answering before any site binds the request.
  A named HTTP platform + an empty body means "no site matched", not "file missing".

STEP 2 - prove it is a wall, not a missing path
  curl -sk -o /dev/null -w '%{http_code} %{size_download}\n' https://127.0.0.1:18443/admin
  expected: 404 0
  same status, same zero length on any path = the router produced it.

STEP 3 - the contrast
  curl -skD - -o /dev/null -H 'Host: ok.corp.lab' https://127.0.0.1:18443/ | tr -d '\r'
  expected:
    HTTP/2 200
    server: Microsoft-IIS/10.0
    content-length: 1487
  Two distinct Server values:
    Microsoft-HTTPAPI/2.0 -> no site matched
    Microsoft-IIS/10.0    -> a site matched and answered

STEP 4 - also true on plain HTTP (some fuzzers only speak :80)
  curl -sk -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/
  expected: 404
  curl -skI http://127.0.0.1:18080/ | grep -i server
  expected: server: Microsoft-HTTPAPI/2.0

STEP 5 - no Host header at all
  curl -sk -o /dev/null -w '%{http_code}\n' --http1.0 -H 'Host:' https://127.0.0.1:18443/
  expected: 404 (still the wall)

NEGATIVE CHECK (keeps the case honest)
  'portal' as a Host is still a 404 here - keyword routing belongs to C10:
  curl -sk -o /dev/null -w '%{http_code}\n' -H 'Host: portal' https://127.0.0.1:18443/
  expected: 404

WHY IT MATTERS
  This is the observation that converts "one boring IP" into a target: the site
  exists, you are addressing it wrong. Next case reads the certificate for names.

TEARDOWN
  make down LAB=c01-bare-ip-404

C02 - CERTIFICATE SAN/CN AS A DISCOVERY SOURCE
================================================
Lab      : c02-cert-san

Ports    : HTTP 18090, HTTPS 18453
Start    : make up LAB=c02-cert-san
Verify   : make verify LAB=c02-cert-san      (11 assertions)

OBJECTIVE
  Read the TLS certificate the IP hands out, turn it into a hostname list, then

STEP 5 - wildcard certificate != wildcard routing
  curl -sk -o /dev/null -w '%{http_code}\n' -H 'Host: zzz.corp.lab' https://127.0.0.1:18453/
  expected: 404

STEP 6 - no SNI still returns the same certificate
  openssl s_client -connect 127.0.0.1:18453 </dev/null 2>/dev/null \

==== LAB: c03-wildcard-hosts ====

C03 - WILDCARD HOST-HEADER FUZZING WITH DECOYS
===============================================
Lab      : c03-wildcard-hosts
Case     : C3 (writeup para 16, 30)
Ports    : HTTP 18100, HTTPS 18463
Start    : make up LAB=c03-wildcard-hosts
Verify   : make verify LAB=c03-wildcard-hosts      (18 assertions)

OBJECTIVE
  The certificate says *.corp.lab and the IP answers 404 to everything.
  Enumerate labels, send them as Host headers, find the one vhost that serves an
  application - without claiming the decoys.

STEP 1 - baseline the noise

  expected: every line ends with the same hash (f94b52ccf1c2)

STEP 2 - find what a real site has and a default page does not
  while read -r w; do
    [ "$(curl -sk -o /dev/null -w '%{http_code}' -H "Host: $w.corp.lab" \
        https://127.0.0.1:18463/robots.txt)" = 200 ] && echo "HIT $w.corp.lab"

  expected: HIT chatadmin.corp.lab

  ffuf -u https://127.0.0.1:18463/chatadmin \
       -H 'Host: FUZZ.corp.lab' -w _shared/data/vhost-labels.txt \
       -fc 403,404 -t 40 -of json -o /tmp/c03.json

    Disallow: /chatadmin/api

  curl -sk -H 'Host: chatadmin.corp.lab' https://127.0.0.1:18463/chatadmin
  expected: the "Chat Admin" shell (357 bytes)

  403 bait - a rule matched, nothing is served:
    curl -sk -o /dev/null -w '%{http_code}\n' -H 'Host: old-portal.corp.lab' \
      https://127.0.0.1:18463/
    expected: 403   (Server: Microsoft-HTTPAPI/2.0 - no site)

    curl -sk -H 'Host: vpn.corp.lab' https://127.0.0.1:18463/chatadmin \

  curl -sk -o /dev/null -w '%{http_code}\n' -H 'Host: chatadmin.corp.lab' \
    https://127.0.0.1:18463/CHATADMIN
  expected: 200

WHY IT MATTERS
  Status and length triage cannot separate ten identical decoys. The signal is
  behaviour on a path only a real application would have. A 403 is a lead about
  a rule, never a finding.

C04 - CONTENT DISCOVERY ON A DEFAULT PAGE
==========================================
Lab      : c04-content-discovery

Ports    : HTTP 18110, HTTPS 18473
Start    : make up LAB=c04-content-discovery
Verify   : make verify LAB=c04-content-discovery      (15 assertions)

OBJECTIVE
  You have a vhost whose root is an IIS default page: nothing to crawl, nothing in
  Wayback. Find the application root with active discovery and tell a hit from bait.

STEP 1 - confirm there is nothing passive to chew on
  curl -sk -H 'Host: chatadmin.corp.lab' https://127.0.0.1:18473/ | grep -o 'IIS Windows Server'
  expected: IIS Windows Server   (the default page)

  ffuf -u https://127.0.0.1:18473/FUZZ -H 'Host: chatadmin.corp.lab' \

==== LAB: c05-js-api-pivot ====

C05 - JS BUNDLE TO SECOND VHOST (404 SIGNATURES)
=================================================
Lab      : c05-js-api-pivot
Case     : C5 (writeup para 44-48)
Ports    : HTTP 18120, HTTPS 18483
Start    : make up LAB=c05-js-api-pivot
Verify   : make verify LAB=c05-js-api-pivot      (16 assertions)

OBJECTIVE
  The SPA calls a backend on another hostname. Prove that hostname is real by
  comparing 404 signatures instead of trusting a string in a bundle - and
  recognise the decoy URL.

STEP 1 - read the bundle
  curl -sk -H 'Host: chatadmin.corp.lab' \
    https://127.0.0.1:18483/chatadmin/assets/app.js | grep -E 'API_BASE|STAGING_API'

  expected:
    API_BASE: "https://chat-api.corp.lab/api",
    STAGING_API: "https://chat-staging.corp.lab/api",

STEP 2 - the signature test (the actual technique)
  curl -skI -H 'Host: chat-api.corp.lab' https://127.0.0.1:18483/nope | grep -i server
  expected: server: Microsoft-IIS/10.0      (a site answered)
  curl -skI https://127.0.0.1:18483/nope | grep -i server
  expected: server: Microsoft-HTTPAPI/2.0   (no site matched)
  Same status code (404), different owner. That is the discriminator.

  Body sizes, if you want the numbers:
  curl -sk -o /dev/null -w '%{size_download}\n' -H 'Host: chat-api.corp.lab' \
    https://127.0.0.1:18483/nope      # 936  (IIS error page)
  curl -sk -o /dev/null -w '%{size_download}\n' https://127.0.0.1:18483/nope   # 0  (the wall)

STEP 3 - the API is live, not just a name
  curl -sk -H 'Host: chat-api.corp.lab' https://127.0.0.1:18483/api/ | jq .
  expected:
    {"users":"/api/users/",
     "auth/password_reset":"/api/auth/password_reset",
     "chats":"/api/chats/",
     "chat-status":"/api/chat-status"}

  curl -sk -H 'Host: chat-api.corp.lab' https://127.0.0.1:18483/api/chat-status | jq .
  expected: {"service":"chat-api","status":"ok","build":"2026.11.1"}
  One working endpoint is what separates a vhost from a string.

STEP 4 - the decoy
  curl -sk -o /dev/null -w '%{http_code}\n' -H 'Host: chat-staging.corp.lab' \
    https://127.0.0.1:18483/api/
  expected: 404
  curl -skI -H 'Host: chat-staging.corp.lab' https://127.0.0.1:18483/api/ | grep -i server
  expected: server: Microsoft-HTTPAPI/2.0   -> it was never a vhost

STEP 5 - the two sites are different applications
  curl -sk -H 'Host: chat-api.corp.lab' https://127.0.0.1:18483/api/ | grep -c 'Chat Admin'
  expected: 0
  curl -sk -D - -o /dev/null -H 'Host: chat-api.corp.lab' https://127.0.0.1:18483/api/ \
    | tr -d '\r' | grep -i content-type
  expected: content-type: application/json

WHY IT MATTERS
  A URL in a bundle is a hypothesis. Two independent signals confirm a vhost: a
  Server header that belongs to a site, and a path that answers with that site's
  application. The decoy has neither - which is how you avoid reporting a hostname
  you invented from a string.

C06 - BROWSER PATH: DNS OVERRIDE, CA TRUST, BROWSABLE API
==========================================================
Lab      : c06-browser-dns
Case     : C6 (writeup para 54)
Ports    : HTTP 18130, HTTPS 18493
Start    : make up LAB=c06-browser-dns
Verify   : make verify LAB=c06-browser-dns      (11 assertions)

OBJECTIVE
  Stop using raw Host headers. Make the hostnames resolve and the certificate
  trusted so the SPA and the API behave like they do for a real user - that is
  where DRF's browsable API and sequence bugs actually show up.

  Browse: https://chatadmin.corp.lab:18493/chatadmin
          https://chat-api.corp.lab:18493/api/

  No /etc/hosts change is needed: every check uses curl --resolve.

  curl -sk -D - -o /dev/null -H 'Host: chat-api.corp.lab' \
    https://127.0.0.1:18493/api/ | tr -d '\r' | grep -i content-type
  expected: content-type: application/json

  curl -sk -D - -o /dev/null -H 'Host: chat-api.corp.lab' -H 'Accept: text/html' \
    https://127.0.0.1:18493/api/ | tr -d '\r' | grep -i content-type
  expected: content-type: text/html; charset=utf-8

  curl -sk -H 'Host: chat-api.corp.lab' -H 'Accept: text/html' \
    https://127.0.0.1:18493/api/ | grep -o 'Django REST framework' | head -1
  expected: Django REST framework

STEP 2 - the SPA is the same deployment, not a separate host
  curl -sk -o /dev/null -w '%{http_code}\n' -H 'Host: chatadmin.corp.lab' \
    https://127.0.0.1:18493/chatadmin
  expected: 200
  curl -sk -H 'Host: chatadmin.corp.lab' \
    https://127.0.0.1:18493/chatadmin/assets/app.js | grep API_BASE
  expected: API_BASE: "https://chat-api.corp.lab/api"

  openssl verify -CAfile _shared/certs/out/ca.crt \
    labs/c06-browser-dns/edge/certs/lab.crt
  expected: .../lab.crt: OK

  It is the certificate actually served:
  openssl s_client -connect 127.0.0.1:18493 -servername chat-api.corp.lab </dev/null 2>/dev/null \
    | openssl x509 -noout -fingerprint -sha256
  compare with:  openssl x509 -in labs/c06-browser-dns/edge/certs/lab.crt -noout -fingerprint -sha256

STEP 4 - no redirect loops (a classic browser-only failure on vhosts)
  curl -sk -o /dev/null -w '%{num_redirects}\n' -H 'Host: chat-api.corp.lab' \

    https://127.0.0.1:18493/api/ | grep -c 'Index of /'
  expected: 0

  Once the browser resolves the vhosts, the browsable API shows endpoint shapes
  (/api/auth/password_reset, /api/chats) that become the input to C07. Note the
  deliberate absence of CORS headers: a report based only on "CORS missing" is not

==== LAB: c08-sni-routing ====

C08 - SNI VS HOST HEADER
=========================
Lab      : c08-sni-routing
Case     : C8 (writeup para 16, SNI detail)
Ports    : HTTP 18150, HTTPS 18513
Start    : make up LAB=c08-sni-routing
Verify   : make verify LAB=c08-sni-routing      (11 assertions)

OBJECTIVE
  Separate the two controls that get conflated in vhost work: SNI picks the
  certificate, the Host header picks the site. Learn what a mismatch actually
  means before you report the wrong thing.

STEP 1 - two certificates, one listener
  U=127.0.0.1:18513
  fp() { openssl s_client -connect $U ${1:+-servername $1} </dev/null 2>/dev/null \
         | openssl x509 -noout -fingerprint -sha256; }

  fp corp.lab
  expected: the public leaf fingerprint (labs/c08-sni-routing/edge/certs/lab.crt)

  fp internal.corp.lab
  expected: a DIFFERENT fingerprint (internal.crt)

  fp nothing.corp.lab
  expected: back to the public leaf (unknown SNI falls back to default)

STEP 2 - the internal certificate names a different zone
  openssl s_client -connect $U -servername internal.corp.lab </dev/null 2>/dev/null \
    | openssl x509 -noout -text | sed -n '/Subject Alternative Name/,+1p'
  expected: DNS:internal.corp.lab, DNS:*.internal.corp.lab   (no corp.lab in it)

STEP 3 - routing ignores SNI entirely
  curl -sk -o /dev/null -w '%{http_code}\n' -H 'Host: app.corp.lab' https://$U/
  expected: 200
  curl -sk -H 'Host: admin.internal.corp.lab' https://$U/ | grep -o 'Internal Admin'
  expected: Internal Admin        (200, while the PUBLIC certificate was presented)

STEP 4 - and the internal certificate unlocks nothing by itself
  curl -sk -o /dev/null -w '%{http_code}\n' --resolve app.corp.lab:18513:127.0.0.1 \
    https://app.corp.lab:18513/
  expected: 200   (public site; SNI choice does not change routing)

STEP 5 - what the 4-way matrix shows
  SNI corp.lab       + Host app.corp.lab              -> 200, public cert, no warning
  SNI corp.lab       + Host admin.internal.corp.lab   -> 200, cert does not match Host
                                                         (browser warning, full access)
  SNI internal...    + Host admin.internal.corp.lab   -> 200, clean
  SNI internal...    + Host app.corp.lab              -> 200, cert does not match Host

WHY IT MATTERS
  A mismatch warning is a certificate observation, not access to the internal zone.
  "The certificate has a different name" is a lead about naming; "the Host header
  reaches a site" is a lead about routing. Two separate findings, each needing its
  own impact. And unknown-SNI fallback is why passive certificate grabs work.

TEARDOWN
  make down LAB=c08-sni-routing

==== LAB: c11-silent-sni ====

C11 - SILENT FRONT END: NO SNI OR NO HOST, NO ANSWER
=====================================================
Lab      : c11-silent-sni
Case     : C11 (your case: routing that drops instead of answering)
Ports    : HTTP 18190, HTTPS 18553
Start    : make up LAB=c11-silent-sni
Verify   : make verify LAB=c11-silent-sni      (20 assertions)

OBJECTIVE
  A front end that answers nothing unless the TLS handshake carries the right SNI
  AND the request carries the right Host. Bare IP, wrong SNI, wrong Host: the socket
  stays open and no byte comes back. Learn to tell silence from 404/403/reset, and
  learn why silence is the hardest evidence to work with.

WHAT YOU GET
  - https://127.0.0.1:18553 and http://127.0.0.1:18190 - nothing answers there.
  - The site is ops.corp.lab (an "Ops Console"). You have to know the name before
    the front end says anything at all.

RULES OF THE LAB
  - require_sni: no SNI or an unexpected SNI stalls the handshake (no ServerHello).
  - require_host: the Host is compared literally (case and port normalised, trailing
    dot NOT normalised). A mismatch is dropped after the handshake, with no status.
  - The front end holds the connection ~10-20s and never writes a byte, so your
    client's own timeout is what you observe.

SUCCESS CRITERION
  bash checks/verify.sh. As a human: you can state which of your tools would have
  reported "nothing here" and why that is not evidence of absence.

HINTS
  1. curl exit code 28 = timeout; 000 as the status alone proves nothing (a reset
     looks similar). Assert on the exit code.
  2. No SNI means no certificate: openssl s_client without -servername gets nothing.
     That is why passive certificate discovery fails against this front end.
  3. On :80 there is no SNI - only Host. Try the name there to confirm it exists
     before blaming TLS.
  4. The allow-list is literal: ops.corp.lab:443 matches, ops.corp.lab. does not.
